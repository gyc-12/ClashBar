## Context

分流页当前只读核心规则，快捷新增仅支持四种目标。用户本地主配置包含 RULE-SET、DST-PORT、MATCH 等类型，需要原位编辑与可搜索策略选择。持久化保持 mihomo 原生格式，配置脱离 App 仍可运行。

## Goals / Non-Goals

Goals：在现有分流页完成编辑、查看自定义项和更换规则策略；正确处理原始索引、重复规则、附加参数及 YAML 注释；复用已有事务保护。

Non-Goals：本轮增加 App 私有规则库或启动合并层、直接改 HTTP/MRS 下载缓存、为远程机器增加文件管理服务、默认展开所有规则集内部条目、批量改策略或拖拽排序。

## Candidates

### A. Edit native rules in place — recommended

- 现有 rules 为数据来源，编辑时原位替换，不自动置顶或去重。
- 新增仍保持置顶；用户自定义项用 YAML 注释标记，正文为标准 mihomo 规则。
- 在全部/自定义视图中展示相同规则，保持原生匹配顺序。手动配置项可明确标记为自定义，不移动规则。
- 最贴合现有架构，能够给不同规则选择不同代理组。需要增加原文定位、注释保留和与运行态的对应关系。

### B. Native file providers for custom rules

- 将自定义匹配条件放入原生 type:file 规则集，主配置以 RULE-SET 引用。
- 自定义集合容易识别，文件可独立管理，但策略属于 RULE-SET 引用，不属于集合内部每个条件。
- 若用户规则需要不同策略，需要拆为多个集合或仍将规则保存到主配置；已有规则的逐条修改仍需要方案 A 的写入能力。
- 适合后续大量同策略规则的集合管理，不推荐作为这三个需求的首版实现。

客户端 prepend/append/delete 覆写方案另作对照：有利于覆盖订阅，但需要客户端合并，与当前原生配置约定不一致，本提案不采用。

## Recommended interaction

1. 保留现有类型筛选、搜索和按策略分组；增加全部/自定义的来源筛选，展示当前配置、原始序号、来源和运行状态。
2. 每条可定位的主规则在悬停及右键提供编辑。编辑器预填原类型、条件、策略和附加选项，展示修改后的原生规则预览。
3. 策略文本改为选择入口，代理组支持搜索并包含隐藏组，提供 DIRECT/REJECT 等有效内置策略。选择后立即走事务保存，保存期间行内显示状态；失败回退显示值。
4. 更换规则策略只修改此规则的目标字段，不调用切换策略组节点的接口。按策略分组时保存完成后该行移入新策略分组。
5. RULE-SET 编辑器可以修改所引用规则集及该引用的策略；界面明确说明修改策略会影响该引用匹配的整个集合。远程集合的单个条件可通过新增更靠前的自定义规则覆盖，覆盖优先级在预览中说明。
6. MATCH 没有条件输入；SUB-RULE 的目标为子规则名，使用专门目标选择器；逻辑规则使用表达式编辑；不能可靠拆分的其他类型允许原文编辑，由核心最终校验。
7. 核心停止时仍可查看及保存本地规则，显示未运行；运行配置与当前编辑文件不一致时显示未应用，不将核心列表索引盲写到当前文件。

## Persistence and identity

- 增加 NativeRuleDocument / NativeRuleEntry 类模型，保留配置路径、原始列表索引、原文、类型、条件、策略、附加参数、源范围、自定义标记和打开时的文件快照。
- UI 筛选索引与源规则身份分离，身份由规范化文件路径及原始索引组成；配置路径的符号链接别名按同一文件核对。重复的相同字符串按源索引区分，保存前对配置快照及目标条目再次检查。
- 普通 YAML 块序列采用源范围替换，保留其他行、注释、附加参数和行尾风格。锚点、流式序列等特殊写法允许等价序列化，但必须保留识别自定义规则所需的标记并核对完整 YAML 语义。
- 实际标记为规则行注释中的 `clashbar:custom` 空白分隔 token。注释标记只是展示来源信息，不承载规则语义；移除注释或脱离 App 后规则仍直接生效。旧快捷新增没有标记，不能准确自动判定，需要显式标记或由用户确认迁入自定义视图。
- 本地 type:file 集合仍通过原有可写条件访问；其条件没有独立策略，修改策略定位到主配置 RULE-SET 引用。HTTP/MRS 原文不直接编辑。
- 整份订阅覆盖更新可能移除本地编辑和注释标记，不隐式重新合并；节点订阅 proxy-providers 更新不等同于主配置覆盖。

## Save and apply

复用 NativeRuleEdit 及 commit：候选构造、独立校验、再次检查并发修改、备份、原子写入、目录监控自身写入确认、应用、刷新列表。主配置使用已有 PUT /configs payload，在校验结束后再次读取 GET /configs，保留运行模式、监听端口和完整 TUN 对象，显式补齐 GET 省略的零值，避免恢复默认 IPv6 地址或选项；本地 provider 条件改动只刷新对应 provider。

普通规则编辑通过 `PUT /configs?force=false` 在现有核心进程内重载，不调用 stop/start/restart 或清空连接接口。mihomo v1.19.31 的 ApplyConfig 仍会重载整个配置并暂时暂停新流量处理；未改变的 TUN 配置不会重建接口，现存普通 TCP 转发没有被该流程统一关闭，但不能将其视为所有协议绝对无中断。新连接可能在重载窗口失败，UDP 数据包可能暂时被丢弃。

应用失败恢复文件并尝试恢复运行态；若恢复时发生外部修改，保留外部修改并提示备份。并发策略修改串行处理；保存期间协调配置切换、订阅更新、核心启停和其他设置写入。

## Risks / Trade-offs

- API 返回的是解析后的规则，不能完整还原原始行；使用本地文件为编辑来源，并对运行态对应情况核验。
- 自定义是来源标记，不意味着更高优先级；自定义视图不能造成规则实际重排。现有条目标记为自定义只修改注释。
- 非标准表达式、SUB-RULE 和跨字段锚点需要类型及 YAML 专门处理，不能通用地 split 逗号。
- 主配置 reload 的行为由核心决定，新规则用于后续连接；本轮不自动关闭或迁移现有连接。
- 表格空间有限，使用行内策略入口和弹出编辑器，不在每行常驻完整表单。

1. 选定方案及自定义来源定义，完善规范和验收边界。
2. 实现规则原文模型、类型解析和原位编辑，覆盖用户现有 56 条规则的类型。

4. 在分流页接入逐条编辑与策略选择，维护筛选和分组时的准确定位。
5. 接入事务应用、状态反馈、中英文及错误恢复；协调原有监控和运行设置。
6. 验证常规类型、复杂规则、重复索引、原顺序、注释、失败及并发；独立核心集成校验包含进程 PID 不变、长 TCP 连接连续性及新连接使用新策略，记录 UDP 重载窗口行为；swift build、swift test、make spec-check 和无核心打包。
